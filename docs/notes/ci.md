# CI and deployments

`.github/workflows/ci.yml` runs `vp run check`, `vp test`, and `vp run build` on pull requests targeting main and pushes to main. A passing same-repository PR deploys `pr-<number>`; a passing push to main deploys `prod`. Fork PRs get validation without deployment credentials. Closing or merging a PR removes its preview, database, feedback namespace, and preview comment. Deployment and cleanup share a per-stage concurrency group and do not cancel running migrations.

GitHub Actions uses Vite+ 1.0.0, Node 24, and the frozen Bun lockfile. Repository secrets are `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `BETTER_AUTH_SECRET` (production), and `PREVIEW_AUTH_SECRET` (separate from production). `GITHUB_TOKEN` is supplied by Actions for the Alchemy-managed preview comment. The existing Cloudflare deployment credential is used; no token-minting admin stack is needed. Alchemy's provider preflight validates Cloudflare credentials before deployment and cleanup.

## Preview data

`stacks/preview-data.ts` owns a separate `MeadowPreviewData` stack, with one `snapshot-<timestamp>` stage per generation and remote Cloudflare state. It clones production into a shared snapshot, removes sessions, impersonation tokens, rate limits, and verification tokens, then writes a readiness marker with the successful sync time. A failed or incomplete snapshot cannot be selected. PR databases clone this sanitized snapshot rather than reading production, then apply their own migrations. Existing users can sign in with their usual passwords. Clones contain real client records and password hashes; Alchemy transfers SQL through runner memory without saving it as a workflow artifact or committed file. Preview feedback stays separate in its own KV namespace.

`vp run preview:data -- if-stale` compares the latest ready snapshot's successful sync timestamp with the current time. Only a newly opened PR requests this mode: if the snapshot is over seven days old, it is refreshed once; otherwise it is reused. Ordinary PR pushes and reopened PRs use `reuse`, which only creates a snapshot if none exists. Snapshot selection/creation is serialized in Actions to avoid duplicate exports. `lookup` is read-only and is used during PR cleanup. These commands require Actions and report only database IDs and sync dates, never client values or dump contents.

`.github/workflows/refresh-previews.yml` runs at 09:00 UTC on the first day of each month. It ensures a snapshot synced in the current month exists, then validates and redeploys each open same-repository PR's merge ref. A newly opened PR earlier that month may already have refreshed the snapshot, in which case the scheduled run reuses it. A bootstrap snapshot is created on the first preview deployment if none exists. The preview database name includes the UTC year and month, so the first deployment each month refreshes it; later deployments in the month preserve preview edits even if a newly opened PR refreshed the shared snapshot. Running the monthly workflow manually in the same month does not reset those previews again.

Snapshot generations are independent, so creating a new snapshot does not delete the previous source during an in-flight clone. Monthly maintenance keeps the latest two ready generations and all snapshots younger than 60 days; older generations are removed through their own Alchemy stacks. Production is only read as the snapshot source; PR migrations and edits target separate databases. A PR whose migrations conflict with the snapshot schema fails rather than modifying production.

Monthly preview refreshes discard preview-only edits. Database replacement is create-first, allowing Alchemy to prepare the new database before rebinding the Worker and removing the old database. This is not a backup or an atomic user-session handover; do not use previews to keep lasting work. Local `dev:local` and automated tests stay isolated; explicitly opted-in `dev:live` still accesses production as documented in the project instructions.

## Activation

The workflows take effect only after their files reach GitHub; a local commit does not activate them. The first production and preview deployments still need a real Actions run to verify provider permissions, cloning, migrations, and cleanup end to end. Branch protection is not changed automatically; requiring the `check` job before merging is a separate repository setting.
